# Рефбек-бот: безопасность и надёжность выплат

Черновик на согласование. Дополняет:
- [PAYOUT_BUSINESS_LOGIC.md](PAYOUT_BUSINESS_LOGIC.md) — бизнес-логика (ранги, кулдаун, 30-дневная экспирация, комса);
- [PAYOUT_ARCHITECTURE.md](PAYOUT_ARCHITECTURE.md) — базовая безопасная архитектура, роли, БД, секреты, сервер.

Этот документ фокусируется на том, чего в старой архитектуре не было: **самостоятельные
выплаты с EVM-кошелька бота** и связанные с этим отказы — Telegram, зависшие кнопки,
жизненный цикл on-chain транзакции, сеть, падение бота — так, чтобы **не потерять деньги
и не обидеть пользователей**.

Обозначения: 💡 — предложение; ❓ — решение к подтверждению; 🔒 — инвариант безопасности
(нарушать нельзя); ✅ — уже зафиксировано.

---

## 1. Инварианты «не проебать деньги» 🔒

Это правила, которые система обязана держать при любом отказе. Всё остальное —
средства их достижения.

1. **Никогда не платить дважды за одно начисление.** Каждое начисление оплачивается
   максимум один раз (ledger `paid`+txid). Ретраи и рестарты не создают вторую выплату.
2. **Никогда не платить больше, чем должны.** `net` считается из зафиксированных
   начислений; никаких «пересчётов на лету» во время отправки.
3. **Платить только на подтверждённый адрес-снапшот.** Адрес фиксируется в момент
   создания выплаты; смена кошелька после этого не меняет направление уже созданной
   выплаты.
4. **Fail closed.** Любая неопределённость (не знаем статус tx, не сходится баланс,
   неполные данные с биржи) → **не отправляем**, ставим на паузу, алертим. Лучше
   задержать выплату, чем отправить лишнее/повторное.
5. **Деньги не «исчезают».** Начисление всегда в одном явном состоянии:
   `accruing → available → reserved → [pending_admin →] paid | expired`. Списание в
   `paid` — только после подтверждения транзакции; `expired` — только по 30-дневному
   правилу. В `reserved`/`pending_admin` экспирация на паузе (см. 6.2).
6. **Всё аудируется.** Каждый переход состояния и каждое действие с деньгами — в
   append-only audit log (кто/что/когда/старое→новое, суммы, txid, nonce).

## 2. Разделение контуров (ключевой принцип)

Как в `PAYOUT_ARCHITECTURE.md`, но приватный ключ EVM-кошелька усиливает требования.

- **bot-app** (Telegram): интерфейс, приём заявок/UID/кошельков, чтение affiliate API
  (read-only ключи), запись в БД. **Не имеет доступа к приватному ключу EVM-кошелька.**
- **accrual-worker**: периодически опрашивает биржи, пишет начисления (append-only),
  считает ранги, помечает экспирацию. Тоже без ключа кошелька.
- **payout-executor**: изолированный процесс/контейнер. **Единственный**, кто держит
  доступ к подписи транзакций. Читает из БД только выплаты в статусе «одобрено к
  исполнению», исполняет строго идемпотентно, single-flight (по одной tx за раз).
- **БД (PostgreSQL)** — источник истины и очередь между контурами.

Если взломают bot-app (Telegram-токен, VPS через бота) — злоумышленник **не** получает
ключ кошелька и не может подписать перевод. Максимум — испортит заявки, что видно в
аудите и ловится инвариантами.

💡 Рассмотреть **вынесенный signer**: executor формирует неподписанную tx, отдельный
мини-сервис/HSM/железо подписывает. Тогда ключ не живёт даже в executor-процессе.

## 3. Telegram — нюансы

### 3.1 Доставка апдейтов
- Telegram доставляет апдейты **at-least-once** — один и тот же апдейт может прийти
  повторно (особенно после сетевых сбоев). 🔒 Обрабатывать **идемпотентно** по
  `update_id` (дедуп в БД/кэше).
- **Только один инстанс long polling.** Два запущенных бота = двойная обработка =
  потенциально двойные действия. Гарантировать single-instance (lock в БД/файле,
  один replica в оркестраторе). `getUpdates` с двух процессов ещё и конфликтует.

### 3.2 Зависшие кнопки / callback-и (важно)
- На каждый `callback_query` обязательно вызывать `answerCallbackQuery`, иначе у
  клиента крутится спиннер — «зависшая кнопка». Даже при ошибке — отвечать.
- **Двойные/тройные тапы**: пользователь жмёт «Вывести» несколько раз, пока идёт
  обработка. 🔒 Защита:
  - каждая финансовая кнопка несёт **токен действия** (nonce), одноразовый;
  - при первом клике атомарно переводим состояние в БД (`available → reserved`
    внутри транзакции с `SELECT … FOR UPDATE`); повторный клик видит, что токен уже
    использован → «уже в обработке», ничего не делает;
  - после действия **клавиатуру убираем/заменяем** (edit message), чтобы старую
    кнопку нельзя было нажать снова.
- **Устаревшие кнопки из старых сообщений**: пользователь скроллит вверх и жмёт
  кнопку месячной давности. 🔒 Токен действия проверяем против текущего состояния;
  протухший/уже использованный → вежливый отказ, без действия.
- **Долгая операция vs таймаут кнопки**: on-chain отправка занимает секунды-минуты.
  Не блокируем обработчик. Паттерн: клик → мгновенно `reserved` + ответ «Заявка
  принята, отправляю, пришлю txid» → executor асинхронно исполняет → уведомление с
  результатом. Кнопка не «висит» в ожидании блокчейна.

### 3.3 FSM и рестарт
- FSM в памяти (как в CLAUDE.md) — ок для навигации по меню, **но не для денег**.
  🔒 Всё финансово значимое (заявка на вывод, резерв) — в БД, не только в памяти.
- Если бот упал посреди диалога — незавершённый flow при рестарте либо безопасно
  сбрасывается (деньги не двигались, т.к. в executor-очередь ещё не попало), либо
  возобновляется из БД. Память терять безопасно.

### 3.4 Прочее
- 429 / flood control от Telegram: очередь исходящих сообщений с бэкоффом; не терять
  критичные уведомления (о выплате) — ретраить.
- Пользователь заблокировал бота / удалил чат: отправка падает (403) — не считать это
  провалом выплаты; выплата уже в блокчейне, уведомление доставим позже/в лог.
- Идентификация: доверять `from.id` из апдейта, а не тексту сообщения. Никаких
  «введите свой TG ID руками» для авторизации.

## 4. EVM-кошелёк и on-chain выплата — нюансы

### 4.1 Приватный ключ (высший риск)
- Ключ живёт **только** в payout-executor (или во вынесенном signer), никогда в
  bot-app, не в общем `.env`, не в git, не в логах.
- Хранение: секрет-файл с правами `600` / Docker secret / KMS; не в переменной
  окружения, если можно файлом. Мастер-доступ отдельно от БД и бэкапов.
- 💡 **Горячий кошелёк держит только оборотный минимум** — сумму под ближайшие
  выплаты + буфер BNB на газ. Основные средства — на холодном/отдельном кошельке,
  пополнение по мере надобности. Взлом executor ≠ слив всей казны.
- ✅ Тест-фаза: **обычный EVM-кошелёк** (приватный ключ в executor), отдельный кош
  только под выплаты. 💡 Сначала гонять на **BSC testnet**, потом mainnet. Вынесенный
  signer/железо — усиление на будущее.

### 4.2 Nonce и single-flight
- 🔒 Транзакции с одного адреса идут по строго возрастающему **nonce**. Параллельная
  отправка двух tx с одним nonce → одна вытеснит другую (риск путаницы/двойной
  отправки). Поэтому executor **single-flight**: одна выплата в полёте, nonce ведём
  и храним в БД.
- Перед отправкой берём nonce = `max(on-chain pending nonce, last_db_nonce+1)`;
  фиксируем `nonce` в записи выплаты **до** броадкаста.

### 4.3 Проблема «отправил, но не знаю, прошло ли» (главный риск двойной оплаты)
- RPC может отвалиться по таймауту **после** того, как tx уже улетела в мемпул. Мы не
  знаем — прошло или нет. 🔒 **Никогда не переотправлять вслепую.** Алгоритм:
  1. перед отправкой пишем `payout: submitting, nonce=N, idempotency_key`;
  2. после броадкаста сохраняем `txhash`;
  3. при любой неопределённости — **сначала проверяем цепочку**: есть ли tx с этим
     nonce/txhash от нашего адреса; если да — считаем отправленной, не шлём вторую;
  4. повторная отправка допустима только как **replacement** (тот же nonce, выше газ),
     а не как новая выплата.

### 4.4 Газ и застрявшие транзакции
- Оценка газа + **потолок** (`MAX_GAS_PRICE`); при всплеске цены газа выше потолка —
  не отправляем, ждём/алертим (fail closed).
- Застрявшая (underpriced) tx: **replacement** с тем же nonce и большим газом. Это не
  новая выплата — idempotency_key и nonce те же.
- Газ (BNB) по бизнес-правилу 5.2/5.3 вычитается из выплаты пользователя — для этого
  нужен курс **BNB→USDT**. ⚠️ Источник курса и `MAX_GAS_PRICE` пока **отложены**
  (реш. §10) → следствие: на тест-фазе **газ из юзера НЕ вычитается, его несёт
  владелец**; вернуть вычет, когда появится курс. Без `MAX_GAS_PRICE` на тесте газ
  контролируем вручную (малый баланс кошелька снижает риск).
- Если `net` < `MIN_PAYOUT` или ≤ 0 — не отправляем, начисления остаются живыми.

### 4.5 Подтверждения и реорги
- Не помечать `paid` сразу после броадкаста. Ждать **15 подтверждений** на BSC (реорги
  возможны). `sent` → `confirmed(15)` → `paid`. ✅

### 4.6 Правильность параметров
- 🔒 Жёстко зашить `chainId` BSC (56), адрес контракта **BEP20 USDT** и его
  **decimals = 18** (не 6, как в TRON/ERC-варианте!). Ошибка в decimals = перевод в
  10^12 раз больше/меньше.
- Адрес получателя: EVM-checksum, не нулевой; USDT — прямой ERC20 `transfer` (approve
  не нужен).
- Округление суммы — вниз до сотых (бизнес-правило), затем корректно в 18-decimals wei.

### 4.7 RPC-провайдер
- Не полагаться на один публичный RPC: **несколько эндпоинтов с фолбэком**, таймауты,
  бэкофф. Провайдер может врать/отставать — критичные проверки (баланс, статус tx)
  сверять, при расхождении — fail closed.
- Egress к RPC — по HTTPS, с таймаутами; учесть rate-limits.

## 5. Сеть — нюансы

- Все внешние вызовы (Telegram, биржевые API, RPC): таймауты + бэкофф. Для бирж это
  уже есть в `base_http` (ретрай только на сеть/5xx/429, не на 4xx).
- 🔒 Ретраить безопасно можно только **идемпотентные** операции. Отправка выплаты —
  **не** идемпотентна на уровне сети: ретрай только через проверку состояния (4.3).
- Неполные данные с биржи (адаптер вернул warning/частичный период): 🔒 не начислять
  «как есть» — помечать период неполным, не включать в доступное к выводу до
  до-получения. Лучше недоначислить сейчас, чем начислить неверно.
- Атомарность БД: каждый переход состояния — в транзакции; при обрыве соединения
  состояние не «повисает» между.

## 6. Падение бота / рестарт / catch-up

### 6.1 Идемпотентность и возобновление
- На старте executor **реконсилит**: для всех выплат в `submitting/sent` проверяет
  цепочку по nonce/txhash и доводит до `paid`/`failed`. Ничего не шлёт заново вслепую.
- accrual-worker и экспирация — **идемпотентны и считаются по времени**, а не по
  «тикам». Пропущенные из-за простоя опросы **до-собираются** (backfill по датам).

### 6.2 Экспирация и простой — честность к юзеру ✅🔒
Тонкий момент «не обидеть»: если бот **лежал**, пользователь физически не мог вывести,
а 30-дневные часы тикали → начисления могли несправедливо сгореть.
- ✅ Ведём журнал доступности сервиса; **продлеваем срок жизни начислений на суммарное
  время простоя** (grace). Кулдаун не продлеваем (простой в пользу юзера).
- 🔒 Начисления в `reserved` / `pending_admin` (ждут исполнения или одобрения админа)
  **не сгорают** — таймер экспирации на них на паузе, иначе задержка админа сожгла бы
  деньги юзера.
- Экспирацию исполнять только когда сервис заведомо «живой» достаточное время после
  подъёма (не сжигать всё сразу в первую минуту после долгого даунтайма).

### 6.3 Инфраструктурная устойчивость
- Авто-рестарт (systemd `Restart=always` / docker `restart: unless-stopped`),
  health-check, алерт разработчику (bot/alerts.py) на падение/рестарт.
- БД: регулярные бэкапы + WAL; периодически тестировать restore.
- Часы: 🔒 **NTP-синхронизация обязательна** — экспирация, кулдаун, границы суток
  (UTC+8) зависят от точного времени. Расхождение часов = неверные сгорания/окна.

## 7. Чтобы не обидеть юзеров (прозрачность и справедливость)

- Показывать понятно: доступно к выводу, в обработке, когда откроется вывод (кулдаун),
  что и когда сгорит, история выплат с txid и ссылкой на скан.
- 💡 Напоминание перед экспирацией (из 5.1): «доступен вывод, иначе X$ сгорит такого-то
  числа».
- При неуспехе выплаты — начисления **возвращаются в живой пул** (не списаны), юзеру
  понятное сообщение, не «молча потерялось».
- При газовом всплеске / net < минимума — не сжигать молча раньше срока; объяснять,
  что сумма копится/ждёт.
- Ошибку адреса после отправки в блокчейн **отменить нельзя** — предупреждать об этом
  явно на этапе добавления/смены кошелька и при подтверждении вывода.
- Owner-контроль без обиды: risk-flag/ручная проверка не должны молча морозить деньги
  надолго — SLA на разбор + уведомление юзеру о статусе.

## 8. Owner-контроль над авто-выплатами ✅

В новой модели вывод инициирует пользователь.
- ✅ **`AUTO_LIMIT` = $200** (net USDT): выплаты ≤ $200 уходят **автоматически**;
  **> $200 — через одобрение admin** (approval-flow: review → authorize → execute).
  Крупные ждут в `pending_admin` (экспирация на паузе, см. 6.2).
- 🔒 **Kill-switch** (admin): мгновенная пауза всех выплат при аномалии.
- **Ручное занижение комсы** (admin, только вниз): при одобрении выплаты admin может
  уменьшить удержанную комсу; сохраняем исходную и переопределённую комсу в `payouts` +
  причину в audit. Инвариант «не платить больше должного» не нарушается — занижение комсы
  **увеличивает** выплату пользователю, а не уменьшает. Повышать комсу выше рангового
  расчёта нельзя (это обидело бы юзера).
- **Разрешение споров по UID** (admin): переназначение/блок `(exchange, uid)` при коллизии.
- Risk-flags (из старого документа): новый юзер, свежесменённый кошелёк, один кошелёк
  у многих TG, резкий скачок суммы, неполные данные адаптера → ручная проверка.
- Дневной/пер-юзер лимиты и timelock для крупных — добавим по мере роста объёмов
  (значения позже).

## 9. Сервер (кратко; база — в PAYOUT_ARCHITECTURE.md §«Защита сервера»)

- VPS: SSH только по ключу, root-логин и парольный SSH выключены, firewall, доступ
  через WireGuard/Tailscale. Бот — long polling, входящих портов не нужно.
- Docker: non-root, `cap_drop: [ALL]`, `no-new-privileges`, `read_only` где можно,
  не монтировать docker socket. PostgreSQL не публиковать наружу, приватная сеть.
- **Изоляция executor**: отдельный контейнер, без Telegram-токена, без входящих
  соединений, egress только к RPC; доступ к ключу — секрет-файлом `600`. Может быть
  остановлен большую часть времени, поднимается под обработку очереди.
- NTP, ротация логов, автообновления безопасности, отдельный unix-user, мониторинг
  падений/аномальных выплат/auth-ошибок.
- Секреты по классам (read-only vs high-risk) — как в старом документе; ключ кошелька
  = high-risk, отдельно от всего.

## 10. Принятые решения (тест-фаза) ✅

1. Подпись — **обычный EVM-кошелёк** (ключ в executor), отдельный кош под выплаты;
   сначала testnet (см. 4.1).
2. Подтверждений до `paid` — **15** на BSC (см. 4.5).
3. **`AUTO_LIMIT` = $200**: ≤ $200 — авто, > $200 — через админа (см. 8).
4. Grace при простое — **да**: срок жизни начислений продлевается на время даунтайма
   (см. 6.2).
5. `MAX_GAS_PRICE` и курс BNB→USDT — **отложено**. Следствие: на тест-фазе газ **не**
   вычитается из юзера, его несёт владелец (см. 4.4). Вернуть перед продом.
6. RPC — подберём пару в процессе (основной + фолбэк, см. 4.7).
7. Хостинг — **свой VPS**; PostgreSQL — свой (не managed).

Вернуться перед продом: вычет газа (курс + `MAX_GAS_PRICE`), конкретные RPC,
дневные/пер-юзер лимиты и timelock для крупных выплат.

**Hardening (бэклог, не в MVP):** фоновая **сверка с биржей** раз в день — по каждому UID
сравнивать сумму наших начислений (paid+live+expired) с тем, что биржа реально начислила;
при расхождении (БД насчитала больше + допуск) — алерт админу. Это ловит баги
accrual-логики / порчу БД, **не** вводя API в путь вывода (БД остаётся авторитетом выплат).
